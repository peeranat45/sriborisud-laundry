# S1 · POC การสแกนบาร์โค้ดผ่านเบราว์เซอร์

**คำถามที่ต้องการคำตอบ** — การสแกนบาร์โค้ดด้วยกล้องมือถือผ่านเบราว์เซอร์ ใช้งานได้จริงในสภาพหน้างานของร้านหรือไม่

**ทำไมต้องทำก่อนทุกอย่าง** — ถ้าไม่ผ่าน การออกแบบ D3 Back Office Scan ทั้งหมดต้องคิดใหม่ และกระทบ A1 Clothes Tracking ซึ่งเป็นระบบที่ระบบอื่นเกือบทั้งหมดพึ่งพา

---

## เกณฑ์ผ่าน

| ตัวชี้วัด | เกณฑ์ |
|---|---|
| เวลาตั้งแต่เล็งจนอ่านติด | ≤ 2.0 วินาที |
| อัตราสำเร็จภายใน 2 วินาที | ≥ 95% จาก 50 ครั้ง |
| สภาพแวดล้อม | แสงจริงในร้าน และต้องทดสอบกับป้ายที่ยับด้วย |

**กรอบเวลา 2 วัน** — ถ้าหมดเวลาแล้วยังไม่ผ่าน ให้ไปแผนสำรองทันที ห้ามไหลต่อ

## แผนสำรองตามลำดับ

1. เปลี่ยนจาก **Code 128 → QR Code** (ทนต่อการยับและรอยเปื้อนมากกว่า)
2. **ขยายขนาดฉลาก** จาก 40×30 เป็น 50×30 หรือ 60×40 มม.
3. เปลี่ยน engine — ถ้า `html5-qrcode` ช้า ลอง `BarcodeDetector` ของเบราว์เซอร์
4. **ซื้อเครื่องสแกนบาร์โค้ด Bluetooth** ~฿1,500 ซึ่งทำงานเป็น keyboard input — ยังใช้เว็บเดิมได้ แค่เปลี่ยนวิธีรับค่า

## วิธีรัน

กล้องของเบราว์เซอร์ทำงานเฉพาะบน **HTTPS** หรือ **localhost** เท่านั้น
การเปิดไฟล์ด้วย `file://` หรือเข้าผ่าน IP ในวง LAN แบบ `http://192.168.x.x` **จะเปิดกล้องไม่ได้**

### วิธีที่แนะนำ — deploy ขึ้น Vercel

```bash
cd poc/s1-barcode-scan
npx vercel --prod
```

ได้ URL แบบ `https://xxx.vercel.app` เปิดบนมือถือได้ทันที

### ทางเลือก — ngrok

```bash
npx serve .            # เปิดที่ port 3000
npx ngrok http 3000    # ได้ URL https ชั่วคราว
```

### ทดสอบบนโน้ตบุ๊กก่อน

```bash
npx serve .
# เปิด http://localhost:3000  (localhost ถือเป็น secure context)
```

## ขั้นตอนการทดสอบ

### 1 · เตรียมฉลาก

เปิด `labels.html` → เลือก **ทั้งสองแบบอย่างละชุด** ขนาด **40×30 มม.** จำนวน 20 ใบ → พิมพ์

> ตั้งค่าในหน้าต่างพิมพ์ให้ **Scale = 100%** และปิด **Fit to page**
> พิมพ์เสร็จ **วัดด้วยไม้บรรทัด** ว่าได้ขนาดตามที่เลือกจริง — ข้อนี้เป็นส่วนหนึ่งของเกณฑ์ผ่าน S2 ด้วย

เตรียมฉลากเพิ่มอีกชุดแล้ว **ขยำให้ยับ** กับอีกชุด **ทำให้เปื้อน** เพื่อทดสอบสภาพจริง

### 2 · ทดสอบ

เปิด `index.html` บนมือถือ → เลือก engine · รูปแบบรหัส · สภาพการทดสอบ → เปิดกล้อง

จากนั้นวนทำแบบนี้ 50 ครั้ง

```
กด "เริ่มครั้งที่ N"  →  เล็งไปที่ฉลาก  →  ระบบบันทึกผลเอง
```

ถ้าเกิน 5 วินาทีระบบนับเป็นล้มเหลวให้อัตโนมัติ หรือกดปุ่ม **อ่านไม่ได้** เองก็ได้

### 3 · ทำซ้ำกับชุดอื่น

ระบบแยกสถิติตาม **engine × format × สภาพ** โดยอัตโนมัติ — เปลี่ยนตัวเลือกด้านบนแล้วตัวเลขจะแยกชุดให้เอง

ชุดที่ควรทดสอบอย่างน้อย

| # | engine | format | สภาพ | จำนวน |
|---|---|---|---|---|
| 1 | BarcodeDetector | Code 128 | แสงปกติ · ป้ายใหม่ | 50 |
| 2 | BarcodeDetector | QR Code | แสงปกติ · ป้ายใหม่ | 50 |
| 3 | html5-qrcode | Code 128 | แสงปกติ · ป้ายใหม่ | 50 |
| 4 | ตัวที่ชนะจาก 1–3 | ตัวที่ชนะ | แสงปกติ · ป้ายยับ | 30 |
| 5 | ตัวที่ชนะ | ตัวที่ชนะ | มือเปียก ถือผ้าอยู่ | 20 |

ชุด 4 และ 5 คือชุดที่สะท้อนหน้างานจริงที่สุด

### 4 · เก็บหลักฐาน

- กด **ดาวน์โหลด CSV** เก็บไว้ที่ `poc/s1-barcode-scan/results/`
- **ถ่ายวิดีโอตอนทดสอบที่ร้าน** 30 วินาที — ใช้ในสไลด์นำเสนอได้ดีมาก
- ถ่ายรูปฉลากที่ใช้ทดสอบ ทั้งแบบใหม่และแบบยับ

### 5 · บันทึกผล

ลงฐานข้อมูล **บันทึกการตัดสินใจ (ADR)** ใน Notion — ประเภท *ผลการทดสอบ POC* · ใช้ในบท *5.2 ผลการทดสอบ POC และการตัดสินใจที่ตามมา*

## สิ่งที่คาดว่าจะพบ

เขียนไว้ล่วงหน้าเพื่อเทียบกับผลจริง — ถ้าผลต่างจากนี้คือข้อค้นพบที่น่าสนใจ

- **BarcodeDetector เร็วกว่า html5-qrcode ชัดเจนบน Chrome Android** เพราะเป็น API ระดับระบบปฏิบัติการ
- **Safari บน iOS ไม่มี BarcodeDetector** จึงต้องใช้ html5-qrcode — ถ้าพนักงานใช้ iPhone ต้องวัดแยก
- **QR ทนป้ายยับได้ดีกว่า Code 128** เพราะมีการแก้ไขข้อผิดพลาดในตัว
- Code 128 กินพื้นที่แนวนอนมาก ฉลากเล็กกว่า 40 มม. อาจอ่านยาก
